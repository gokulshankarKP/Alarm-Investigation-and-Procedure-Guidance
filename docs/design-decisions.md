# Design decisions

| # | Decision | Why | Alternatives considered |
|---|---|---|---|
| 1 | **FastMCP (official `mcp` SDK), streamable HTTP, stateless + JSON responses** | Standard SDK, typed tools from Python signatures with generated input and output schemas. Streamable HTTP makes the server independently deployable. Stateless mode scales horizontally and suits per-request trace headers. stdio is also supported for MCP Inspector and desktop clients. | Custom JSON-RPC (reinventing the protocol); SSE transport (deprecated). |
| 2 | **Copilot uses `langchain-mcp-adapters` for the MCP client, LangGraph for orchestration** | Required stack. Adapters provide discovery and conversion to LangChain tools, with structured content returned as artifacts. LangGraph gives explicit, testable nodes, conditional routing, runtime context injection (the MCP session isn't persisted) and a checkpointer for conversation memory. | A free-form ReAct agent: unreliable tool selection with an 8B local model, hard to test, and it can't guarantee RAG runs in the same workflow. |
| 3 | **Intent-driven, data-dependent workflow instead of a free agent loop** | Every question gets the right chain, each tool's arguments come from earlier tool outputs, and failures degrade predictably. It isn't hard-coded: 10 intents, entity extraction, focus-alarm selection from data, analytics chosen per intent, RAG queries built from MCP results. | ReAct / planner LLM: 5–10 LLM round trips per question are impractical on CPU (qwen3:8b ≈ 4 tok/s here). |
| 4 | **Hybrid intent detection (rules first, LLM when not decisive)** | The rules cover the assignment's question shapes deterministically and instantly. The LLM handles ambiguous phrasing and follow-ups. All LLM output is validated (enum intents, entity patterns, site allow-list), and an off-topic question can't be escalated into tool use. `COPILOT_INTENT_MODE=llm` forces the LLM. | LLM-only (≈ 40–60 s extra per question on CPU, non-deterministic tests). |
| 5 | **Structured JSON synthesis, rendered to Markdown in code** | The model writes less, so it's faster on CPU. Every cause and action carries citation ids that are validated. The GUI panels use the same structure. | Free-text answers (citations unverifiable). |
| 6 | **Deterministic composer as fallback (and `LLM_PROVIDER=none`)** | The system still produces grounded, cited answers when the LLM is slow, down or disabled, and CI needs no model. | Fail the request. |
| 7 | **Deterministic consistency rules for API recommendations vs documents** | Safety-relevant conflicts (restart after trip, spare into restriction, bypass or setpoint changes) must not depend on LLM judgement. Only controlled, active documents count. | LLM-only comparison. |
| 8 | **pgvector hybrid retrieval with RRF + exact alarm-code boosts** | Alarm codes are exact identifiers that embeddings blur. Full text plus code matching makes "BFP-VIB-HH" land on SOP §5.2. Postgres was already provided, and metadata filters are plain SQL. | Pure vector search; a separate vector DB. |
| 9 | **Section-level chunks with denormalised metadata** | Precise citations (§5.2), single-table filtering, heading context in the embedding. | Fixed-size token windows (sections split mid-procedure). |
| 10 | **Two retriever backends behind one protocol** | pgvector in production; an in-memory backend (plus hashing embedder) runs the full ranking logic in CI and offline. | Mocks (would not test ranking). |
| 11 | **The API token lives only in the MCP server** | Enforces "the copilot must use MCP": the backend has no Alarm API credentials or client. Separate MCP bearer token. | Shared token. |
| 12 | **Simulator seed data aligned with the corpus** | MCP and RAG evidence tell the same story, so combined reasoning is demonstrable and testable (DA-101 → BFP cavitation, PCV-210 → compressors, TR-501 → motors). Includes deliberately unsafe API recommendations. | Random data (no meaningful correlation). |
| 13 | **Fault injection built into the simulator** | Retries, timeouts and partial failures are demoable in the GUI and testable end to end over real HTTP. | Only mocked failures. |
| 14 | **Typed contracts everywhere** (pydantic models for API requests, MCP outputs, copilot responses, document metadata) | Input and output validation, generated schemas, fewer integration bugs. | Loose dicts. |
| 15 | **Single Docker image, one command per service** | Faster builds, identical dependency set. | One image per service. |
| 16 | **Hyphenated folders per the required repo layout, mapped to packages** | Matches `apps/backend`, `mcp-servers/alarm-management`, … exactly. `pyproject.toml` (`package-dir`), `PYTHONPATH` in Docker/CI/Makefile and pytest `pythonpath` make them importable. | Renaming folders (deviates from the required structure). |
